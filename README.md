# Automated Security MBR Dashboard

An automated weekly/monthly business-review (MBR) dashboard for security leaders, generated by Claude Code slash commands from any combination of vuln-management, GRC, and IR data sources via MCP.

The dashboard is a **single self-contained HTML file**. Data and rendering live in two separate `<script>` blocks, so the weekly refresh only ever touches data — a bad MCP run cannot break the UI.

This bundle is reference-implementation-agnostic. The skills assume three categories of source (vuln management, GRC, IR), but the actual MCP servers, field names, team IDs, frameworks, and risk taxonomies are yours to configure.

```
    └── ir-risk-mapping.json           ← IR project → risk mapping
```

## How it works (one paragraph)

`/security-report` pulls live data from your configured MCPs in parallel batches, computes a set of derived metrics (deltas, MTTR, SLA compliance, a weighted composite risk grade, per-risk inherent/residual scores), cross-references findings against risks via CWE, builds attack paths and SLA-breach predictions, then injects a single data block between the two markers in `security-posture-report.html`. Renderer untouched. Validation runs before save. Metrics are appended to `security-metrics-history.json` so next week's deltas have something to compare against.

The cross-source layer (CWE-to-risk mapping, IR-to-risk evidence, attack-path chaining) is what makes this a dashboard instead of three separate reports. **Maintain those mapping files.**

## Installation

1. **Drop the skill files into Claude Code commands:**
   ```bash
   mkdir -p ~/.claude/commands
   cp skills/security-report.md ~/.claude/commands/
   cp skills/rewrite-dashboard.md ~/.claude/commands/
   ```

2. **Drop the data files into Claude Code data dir:**
   ```bash
   mkdir -p ~/.claude/data
   cp data/*.json ~/.claude/data/
   ```

3. **Place the dashboard template where the skill expects it:**
   ```bash
   cp dashboard/security-posture-report.html ~/Downloads/
   ```
   (Paths are hardcoded in `security-report.md`. If you move the template, update the skill.)

4. **Configure MCP servers** for whichever data sources you use. The reference architecture assumes:
   - A **vulnerability-management** source — findings, teams, products
   - A **GRC / risk-register** source — risks, controls, frameworks, tests
   - An **incident/IR ticketing** source — IR projects with risk/attack-path mappings

   Edit `skills/security-report.md` to match your MCP tool names and field shapes.

5. Test with `/security-report` in Claude Code. Open the resulting HTML in a browser.

## Weekly run

In Claude Code:

```
/security-report
```

The skill will:
1. Pull from each configured source (vuln source in parallel batches, GRC paginated, IR).
2. Compute trend deltas, MTTR, SLA compliance, weighted composite risk grade.
3. Cross-reference findings → risks via CWE; build attack paths and gap proofs.
4. Inject the new data block into `security-posture-report.html` with a single `Edit` between `===REPORT_DATA_START===` and `===REPORT_DATA_END===`.
5. Validate (file > minimum size, required top-level fields populated, both `<script>` blocks pass `node --check`).
6. Append this week's KPIs to `security-metrics-history.json` (keep the rolling buffer bounded).

Open the resulting HTML in a browser. Publish only if validation passed.

## Configuration to tune for your environment

| File | What to tune | When |
|---|---|---|
| `skills/security-report.md` | MCP tool names, team ID list, field shapes | Initial setup; when a new team is onboarded |
| `data/cwe-risk-mapping.json` | CWE → risk-category mappings | A new CWE appears in findings and isn't linking to a risk |
| `data/ir-risk-mapping.json` | IR project → risk + attack-path mappings | IR opens a new project |
| `dashboard/security-posture-report.html` | UI layout, sections, charts | Only via `/rewrite-dashboard` — never hand-edit the renderer if you can avoid it |

## Architecture notes

- **Two `<script>` blocks, by design.** `<script id="report-data">` is the only thing the weekly skill touches. The other `<script>` is rendering and must never be modified by the data refresh. This separation is what makes the system safe to automate.
- **Markers, not regex.** Data is injected between literal `===REPORT_DATA_START===` and `===REPORT_DATA_END===` strings. If either marker is lost, the skill refuses to overwrite.
- **History is append-only.** The rolling KPI buffer in `security-metrics-history.json` powers every sparkline and delta on the dashboard. Do not truncate it; the skill rotates it.
- **No build step.** One HTML file, Chart.js via CDN (with SRI pinned), web-fonts via CDN. Open it locally, host it as a static file, attach it to a ticket — it works anywhere.
- **False positives are never rendered.** Hard rule in both skills.

## Common failure modes

| Symptom | Likely cause | Fix |
|---|---|---|
| Dashboard shows zeros everywhere | MCP token expired; skill fell back to history with no current data | Rotate the failing MCP token; re-run |
| New team's findings missing | Team ID not in the skill's team list | Add the team ID to `security-report.md` |
| Finding count high but no risk linked | CWE not in `cwe-risk-mapping.json` | Add the CWE → risk pair |
| Validation step refuses to save | Renderer `<script>` has a syntax error (recent UI edit) | Check `node --check` against the renderer block; fix before retrying |
| `===REPORT_DATA_*===` markers gone | Someone hand-edited the template | Re-run `/rewrite-dashboard` to rebuild from scratch |
| Chart.js SRI mismatch in browser | CDN version bumped | Re-pin the `integrity` hash in `rewrite-dashboard.md` |

## When to use `/rewrite-dashboard`

**Only when you're intentionally changing the UI** — adding a section, restyling, restructuring. It rebuilds the whole template and copies the current data block over.

The weekly `/security-report` skill must **never** call `/rewrite-dashboard`. If a refresh fails, fix the refresh — don't rebuild the renderer.

## Data sources

The reference implementation pulls from three categories of source:

- **Vulnerability management** — findings (severity, status, age, mitigation date), teams, products. Powers triage funnel, MTTR, SLA, per-team heatmap, active critical/high tables.
- **GRC / risk register** — risks, controls, frameworks, test pass / doc rates. Powers the risk register, compliance scorecards, control validation, gap proofs.
- **Incident / IR ticketing** — incidents and investigations. Used for likelihood calibration on risks and as evidence on attack paths.

The value of the dashboard isn't any one source — it's the **cross-source layer** that maps findings → risks → controls → incidents into a single decision-making view.
